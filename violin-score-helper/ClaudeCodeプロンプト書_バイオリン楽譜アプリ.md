# Claude Code キックオフ・プロンプト書：バイオリン楽譜アプリ

このファイルは、Claude Code に貼り付けて開発を開始するためのプロンプト集。
`要件定義書_バイオリン楽譜アプリ.md` を同じリポジトリに置き、それを正典として参照させる。

---

## 使い方

1. 新規リポジトリ（例：`violin-score-helper`）を作る。
2. `要件定義書_バイオリン楽譜アプリ.md` をリポジトリ直下に置く。
3. 下の「§0 初回プロンプト」を Claude Code に貼る。
4. 以降、各フェーズのプロンプトを順に実行する。**フェーズをまたぐたびに動作確認**してから次へ進む。

---

## §0 初回プロンプト（プロジェクト理解＋設計合意）

```
あなたはバイオリン学習支援Webアプリを実装するシニアエンジニアです。
同じリポジトリの `要件定義書_バイオリン楽譜アプリ.md` を熟読してから作業してください。

【アプリ概要】
バイオリンの楽譜写真をアップロードすると、
(1)使う弦を色分け (2)指番号 (3)半音マーク(^/v) を自動付与し、
(4)練習用音源をテンポ調整付きで再生でき、(5)タップで手動修正・(6)PNG/PDF保存できる、
スマホ・PC対応のレスポンシブWebアプリ。対象は初級〜中級の生徒。
方針は「100%全自動」ではなく「自動判定＋手動修正」。

【技術スタック（確定）】
- Next.js(App Router) + TypeScript + Tailwind CSS、Vercelデプロイ想定
- 楽譜読み取り(OMR)は Vision対応モデルのAPIで画像→構造化JSONに起こす方式。
  ※ モックデータ・ダミー・シミュレーションは一切使わない。必ず実APIで実装する。
- 判定ロジック（弦判定/指番号配置/半音マーク）は純粋関数モジュールに分離し、ユニットテスト可能にする
- 描画は元画像の上にSVG/Canvasの座標ベースのオーバーレイ
- 弦色は半透明（乗算合成）で符頭が透ける「蛍光マーカー風」
- 音源は Tone.js 等の Web Audio、テンポスライダー付き
- 書き出しは Canvas→PNG、PDF出力

【まず最初にやること】
実装コードはまだ書かないでください。先に以下を提示して合意を取ってください：
1. このアプリの「理想ゴール」をあなたの言葉で3行以内で要約
2. 現状（ゼロから）と、ゴールまでに埋めるべき差分（=作るべきモジュール一覧）
3. ディレクトリ構成案とデータモデル（音符1つを表すJSONの型定義）
4. OMRのAPI呼び出し設計（入力画像→返すJSONスキーマ）。
   JSONには最低限：音高(pitch)、オクターブ、小節index、符頭のbbox座標(x,y,w,h)、
   楽譜に書かれた指番号(あれば)、ローマ数字(あれば)、強弱/松葉記号(あれば)、
   スラー/タイ(あれば)、重音フラグ を含めること

上記4点を出したら止まって、こちらの確認を待ってください。
```

## §1 デザイントークン＋型定義＋スキャフォールド

```
要件定義書の §4.3 / §4.7 の確定値でデザイントークンを定義し、
プロジェクトの土台を作ってください。

【弦の色（蛍光マーカー風・符頭が透ける半透明で使う）】
G線(茶): #8B5A3C / D線(緑): #00BFA5 / A線(赤): #FF4081 / E線(黄): #FFD740

【半音マークの色】
青(指を密着): #006CD4 / 水色(密着しない): #6EE6FF

【ローマ数字→弦】 Ⅰ=E線, Ⅱ=A線, Ⅲ=D線, Ⅳ=G線

   （§0で合意したJSONスキーマに一致させる）
4. トップページに「画像アップロード領域」と「結果表示キャンバス」の空の枠だけ配置
5. `npm run dev` で起動確認できる状態にする

弦名文字(G/D/A/E)のテキスト表示は不要。実装しないこと。
```

## §2 楽譜読み取り（OMR：画像→構造化JSON）

```
アップロードされた楽譜画像を Vision対応モデルのAPIに渡し、
要件定義書 §5 と §0合意スキーマに沿った構造化JSONを返す機能を実装してください。

要件：
- モック禁止。実APIで画像を解析する。APIキーは環境変数(.env.local)で扱い、コードに直書きしない
- 返却JSONは音符ごとに：音高/オクターブ/小節index/符頭bbox(x,y,w,h)/
  楽譜記載の指番号/ローマ数字/強弱・松葉記号/スラー・タイ/重音フラグ
- 1ページ単位で処理（複数ページ一括は対象外）
- 解析結果を画面に「デバッグJSONビュー」として一時表示できるようにする（後で隠す）
- 撮影ムラ・傾きに強くするため、プロンプト側で「五線・符頭・加線・既存の指番号や
  ローマ数字・強弱記号・スラーを座標付きで抽出する」よう明確に指示する

テスト：提供4曲（リーディングのコンチェルト／ホーム・スイート・ホーム／
マジャールの踊り／バッハVn協奏曲No.1 1mov.）の画像で、
音高と符頭座標がどの程度取れるか確認できるログを出すこと。
```

## §3 弦判定ルールエンジン（★最重要・先にテストを書く）

```
要件定義書 §4.4 の弦判定ルールを純粋関数として実装してください。
ロジックが心臓部なので、実装前に必ずユニットテストを先に書きます。

実装するルール（優先順位＝番号順）：
- R1 明示優先：楽譜に指番号(0〜4)があれば絶対採用。無い音は直前ポジション維持。
  ポジションチェンジ不可避な時のみ R2以降へ
- R2 ローマ数字で弦固定（Ⅰ=E, Ⅱ=A, Ⅲ=D, Ⅳ=G）
- R3 「0 vs 4」判定：
   ・第1ポジションで同音になる3ケース → レ(D線0/A線4), ラ(A線0/D線4), ミ(E線0/A線4)
   ・次が高→開放弦0 / 次が低→第4指4 / 同音→次に変わる音の方向 / 末尾→4
- R4 ポジション：奇数ポジション優先、第2ポジション回避（明示時のみ従う）
- R5 トリル：1-2/2-3優先、3-4回避（他に選択肢が無い時のみ許可）

運指モード：
- ①おまかせ（初〜中級） / ②開放弦優先（第4指=小指を避ける）
- ①内でユーザー独自ルールを差し込める余地を関数シグネチャに用意（初期は空でよい）

重音：両方の音にそれぞれの弦色を割り当てる。

【必須テストケース（R3検証）】
- E線0 vs A線4 で次がFis(E線1・高音) → E線0 を返す
- E線0 vs A線4 で次がD(A線3・低音) → A線4 を返す
- フレーズ末尾で0/4が拮抗 → 4 を返す

テストが緑になってから、§2のJSONに弦割り当てを付与する処理を繋いでください。
```

## §4 オーバーレイ描画（弦色・指番号・半音マーク）

```
判定結果を元画像の上に重ねて描画してください。要件定義書 §4.3/§4.6/§4.7 に厳密に従います。

【弦色（§4.3）】
- 符頭に直接、蛍光マーカー風の半透明（乗算/multiply合成）で色を乗せ、音符が透けて見えるようにする
- 元画像に重ねて表示
- 例外：指番号が音符の上部と下部の2種類に分かれて表示されている楽譜では、
  それぞれの指番号の上に色付けする

【指番号の配置ロジック（§4.6）】
- デフォルトは音符の上側
- 下側にするのは以下いずれか：
  ①加線が多い高音域で上部に空きが無い ②元楽譜が既に下部印字 ③重音の下の音
  ④【最優先の距離ルール】符頭から上部配置予定位置までの距離が閾値(px)を超える
   （連桁が密集する16分/32分地帯、符頭が低く棒が上に長い等）→符頭に近い下へ
- ★例外(④より優先)：下に置くと松葉記号や強弱記号(p/mf/f)と重なる場合は、
  記号の視認性を優先し、離れても上側へ置く
- スラー・タイの細線は透過するので重ねてよい

【半音マーク(§4.7)】
- 指番号(数字)に紐付けて近くに置く
- 指番号が上側→ ^（数字の上）、下側→ v（数字の下）
- 色：青#006CD4=同弦で隣接指の密着(1→2,2→3,3→4と逆) /
      水色#6EE6FF=半音だが密着しない(同指クロマティック/シフト/移弦)
- 表示切替：「青のみ」/「青＋水色」をユーザーが切替できる

閾値(距離ルールのpx)は定数化し、後から調整できるようにすること。
```

## §5 手動修正

```
要件定義書 §4.8 の手動修正を実装してください。
- 音符（または判定結果）をタップ/クリックすると、弦と指番号を変更できるUI（ポップオーバー等）
- 変更したら、半音マークの向き・色など下流表示を再計算して即反映
- スマホのタップ操作でも押しやすいターゲットサイズにする
```

## §6 練習音源＋テンポ調整

```
要件定義書 §4.9 の音源機能を実装してください。
- 読み取った音高列から Tone.js 等で簡易音源を生成し、再生/停止できる
- テンポスライダーで速度変更（ゆっくりから合わせられる）
- 完璧な演奏音源ではなく「練習確認用」で割り切る（強弱/アーティキュレーションは対象外）
- 再生位置が分かるよう、鳴っている音符をハイライトできると尚良い
```

## 全フェーズ共通の禁止・厳守事項

- **モックデータ・ダミー・シミュレーション禁止**。OMRは必ず実APIで実装する。
- **APIキーは環境変数**で扱い、ソース・会話・コミットに平文で残さない。
- 弦名文字(G/D/A/E)のテキスト表示は**しない**。
- 弦色は必ず**半透明で符頭が透ける**こと（不透明で塗りつぶさない）。
- 判定ロジックは**純粋関数＋ユニットテスト**を維持する（後から顧客ルールを微調整できるように）。
- 各フェーズ完了時に**動作確認してから次へ**。勝手に全フェーズを一気に進めない。
- 距離閾値・色・弦判定ルールなど**顧客が今後調整しうる値は定数化**して1箇所にまとめる。
